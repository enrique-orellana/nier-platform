# Standard Layout Face Tracking in the Editor Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (or `superpowers:executing-plans` for inline execution) to implement this plan.

## Goal

Add an optional, per-section face-tracking switch for Standard layout sections in the project editor. The switch defaults to Off, Streamer Stack sections do not expose it, enabling it analyzes the master source with the existing YOLO-based tracking pipeline, and the resulting normalized crop keyframes are reused automatically by both the interactive preview and the final Remotion export.

The implementation must keep tracking data deterministic and cacheable. A cache hit must be used without another model run; a source/range/output-dimension/algorithm change must invalidate the cached track; and a failed or pending analysis must never silently render a partially tracked section.

## Architecture

The feature has four layers:

1. The editor timeline model owns the section-level `face_tracking_enabled` flag and validated `face_tracking_cache` payload. Splitting or changing the source range invalidates the cache. Switching the flag off preserves the cache so turning tracking back on can reuse it.
2. The project editor calls a new project-clip face-tracking endpoint. The Go API resolves the cached master source, computes and checks a deterministic cache key, and invokes the Python worker only on a miss. The worker returns a serializable normalized crop track generated by the existing YOLO person candidates, `SpeakerTracker`, `SmoothedCameraman`, and person fallback logic.
3. Both the dashboard preview composition and the root Remotion export composition resolve a cached track at the current frame and use the same crop-style calculation. Standard sections use the tracked crop only when the section flag is enabled and a valid cache is present; otherwise they retain the existing centered Standard layout.
4. Export preparation ensures every enabled Standard section has a valid cache before saving/rendering. Existing caches are reused automatically, and misses are analyzed before the render request is created. Streamer Stack behavior and its existing framing controls remain unchanged.

**Before editing symbols:** run GitNexus upstream impact analysis for `Server`, `NewServerWithDependenciesAndScheduler`, `clipRoutes`, `transcribeProjectClip`, and `OperationClient.Run`. Warn on HIGH/CRITICAL results before editing.

**Tests first:** add `httptest` coverage for:

- `POST /api/clip/{jobID}/{clipIndex}/face-tracking` rejects non-POST requests, malformed JSON, invalid ranges, missing projects, missing masters, and missing Python workers with useful status codes.
- A valid request resolves the project master from the job result and never accepts an arbitrary client filesystem path.
- A cache hit returns the stored track without calling the operation client.
- A cache miss invokes exactly one `face_tracking` worker operation, persists the returned result under the job-scoped render cache, and returns `cache_hit: false` plus the cache payload.
- Repeating the same request hits the cache; changing source fingerprint, range, source dimensions, or algorithm version misses it.
- Concurrent requests for the same cache key do not run duplicate analyses.
- Cache files are constrained below the project output directory and malformed cache files are ignored and replaced.

**Implementation:** extend `clipRoutes` to recognize the new `face-tracking` segment. Add a handler that:

- parses `{start_seconds, end_seconds, source_width, source_height, algorithm_version}`;
- resolves the job/clip master using the same safe filename and job-root rules as project transcription;
- verifies the requested section range is within the clip/master range;
- computes a deterministic key from the canonical master path identity, file size/mtime fingerprint, absolute source range, dimensions, and algorithm version;
- checks `render-cache/face-tracking/<cache-key>.json` below the job root;
- serializes per-key in-flight work so simultaneous editor requests share one result;
- calls `translationRunner.Run` with operation `face_tracking` only on a miss, passing the server-resolved source path and validated range;
- validates the worker result with the same track constraints before writing it atomically;
- returns `{ cache_hit, cache_key, algorithm_version, source_fingerprint, source_start_seconds, source_end_seconds, source_width, source_height, track }`.

Keep the cache independent of version IDs so version branching and repeated editor sessions reuse analysis. Do not trust a client-provided cache key or source path. Use the existing output directory/job-root configuration and `safePath` checks.

**Verification:** run `gofmt` on changed Go files and `go test ./internal/httpapi ./internal/workers` from `backend-go`.
